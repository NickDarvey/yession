# Plan 21 — tokens that expire

[Plan 14](14-git-repos.md) told the operator to register their GitHub App with **user-token
expiration disabled**, and that instruction was never a policy. It was a shape: the device
flow's result went to the Manager through the broker's *paste* path, which stores
`BrokeredStatic` — a credential `needsRefresh` returns `false` for, unconditionally. A token
that cannot rotate must not expire, so the App had to be told not to expire it, and a
permanent user token sat in the secrets file with revocation-at-GitHub as the only way back.

This plan removes the instruction rather than working around it.

## What was already there

Nearly all of it. [Plan 08](08-connections-and-claude-auth.md) put the broker in the Manager
precisely so refresh would be possible without handing refresh tokens to sessions, and Claude
connections have refreshed through it since:

| | |
|---|---|
| `Broker.Resolve` | refreshes a due grant on use — no timer, no background sweep |
| `BrokerFlow.needsRefresh` | five-minute margin, so a turn never starts on a token about to lapse |
| `BrokerFlow.merged` | keeps the previous refresh token when a provider omits it |
| `OAuthGrant` | already carried `RefreshToken`, `ExpiresAt`, `TokenUrl`, `ClientId`, `Dialect` |

So the work was not "build refresh". It was letting a grant the SESSION obtained itself arrive
as a grant.

## The one verb

`SessionConnections.Put` carries a bare string, because a pasted PAT *is* a bare string. The
device flow is not that: it is a whole authorization the session runs end to end (RFC 8628),
and by the time it finishes there is no code left for the broker to exchange — only tokens.
So there is now a sibling that carries what it produced:

```
POST /control/connections/put-grant
  { target, accessToken, refreshToken?, expiresIn?, refreshTokenExpiresIn?,
    tokenUrl, clientId, tokenDialect }
```

Both paths survive because the difference is the point: a pasted token is static and cannot
rotate; this one can, and the type says which is which. `PutGrant` is gated by the same
`ConnectCredential` action — the caller is connecting a credential to a scope it owns, and
whether that credential can refresh itself is a fact about the credential, not a second thing
to permit.

The lifetimes cross the wire as the provider stated them (seconds from now) and become
instants at the Manager, because the clock every later refresh decision is made on is the
Manager's.

## Why this works for GitHub without a client secret

GitHub requires `client_secret` to refresh a user access token **unless the token was
generated by the device flow** — which is ours. The Plan 08 broker is a PKCE public client
that holds no secret and never will, so any other GitHub flow would have needed the
"confidential-client" work Plan 14 deferred. The device flow is the one that fits, and it fits
exactly.

GitHub's user token lives 8 hours and its refresh token 6 months. The token endpoint takes a
form body and answers JSON when asked to (`accept: application/json`, which the broker already
sends), so `FormEncoded` is what the grant records and the existing refresh request works
against GitHub unchanged.

## Three things expiry exposed

**A refresh token can itself lapse.** Six months of not using a session is not exotic. The
grant now records `RefreshExpiresAt`, and a resolve past it refuses with *"the refresh token
has expired — sign in again"* rather than spending a round trip on a grant that cannot
succeed. "Try later" and "sign in again" are different instructions and the caller acts on
them differently.

**Two concurrent resolves both refreshed.** A provider that rotates hands back a new refresh
token and spends the old one, so two resolves of one due grant leave the loser holding a grant
minted from a spent token. This is ordinary rather than exotic here: a session resolves per
turn *and* per network verb. `Broker.Resolve` now holds one in-flight refresh per target and
everyone awaits it — a promise rather than an `Async`, because an `Async` re-runs on each
await, which is the duplicate the map exists to prevent.

**A failed refresh looked like anonymity.** `resolveGitHubToken` fell back to the ambient
`GITHUB_TOKEN` on any resolve error, and a failed refresh is exactly that error — so a
rotation problem presented as "git is anonymous", which sends whoever debugs it at the wrong
thing, and could quietly act as a different identity than the one that was connected. A
connected credential that will not resolve is now a fault, said out loud. The ambient token
stays what it always was: the answer when nothing is connected at all.

## Stated, not fixed

A credential forwarded into a WorkSandbox is baked into its policy env at creation, so a
refreshed token does not reach a sandbox already running: terminal git inside a sandbox older
than the token's life will start failing auth, and the fix is a new sandbox. Withholding
refreshable credentials from sandboxes instead would break terminal git for everyone today in
order to fix it for a long-lived sandbox, so this stays recorded in `docs/GAPS.md` rather than
traded.

A refresh still broadcasts no connection-status frame, so the panel shows a healthy connection
whose refresh is failing until a turn says otherwise. Unchanged by this plan, and now more
reachable — worth an indicator when someone hits it.

## Migration

None. A GitHub credential stored before this keeps working exactly as it did — static, and
still requiring an App that does not expire its tokens — and becomes refreshable the next time
its owner signs in. The envelope gained one optional field, which is the same additive move
`dialect` made before it.
